## 0. 요약

**S1의 근본 원인은 단일 버그가 아니라 비용함수 설계다.**

`q_dist = 0`으로 두고 바운더리 밖 샘플을 버리는 방식(free-corridor + rejection)은 레이싱 MPPI의 정석이고 의도도 맞다. 문제는 그 방식이 성립하려면 필요한 전제 세 가지가 현재 코드에 없다는 것이다.

1. **horizon이 out-in-out을 담을 만큼 길어야 한다** → 현재 1.75 s = 7 m. 부족하다.
2. **feasible set 안에서 최적해가 경계면에 붙지 않도록 하는 항이 있어야 한다** → 없다. 그래서 최적해가 항상 벽에 딱 붙고, 전 샘플 infeasible이 상시 발생한다.
3. **feasible set이 비었을 때의 행동이 별도로 정의되어야 한다** → 없다. racing cost를 살짝 비튼 순위를 쓰는데, 그 순위가 "늦게·멀리 박기"를 선호한다.

여기에 상태추정(슬립각 0 고정)과 충돌 판정(점 하나 + 원)의 낙관적 오차가 겹쳐 남은 마진을 갉아먹는다.

## A. 비용함수 설계

### A-1. `q_dist = 0` + rejection 접근에 대한 판단

**의도**: 센터라인 추종을 끄고 트랙 폭 전체를 자유도로 줘서, 추월 라인과 레이싱 라인을 옵티마이저가 알아서 찾게 한다.
**판정**: 골격은 맞다. 다만 세 가지가 틀렸다.

#### (a) horizon이 목적에 비해 짧다

```
T = 50, dt = 0.035  →  1.75 s
4 m/s 기준 예측 거리 = 7.0 m
map1 트랙 전장 = 25.6 m (센터라인 256점 × 0.099 m)
```

out-in-out 라인은 **진입 직선 + 코너 + 탈출 직선**을 한 번에 봐야 나온다. 대략 12~15 m다. 7 m 시야에서 "진행량 최대화"의 최적해는 레이싱 라인이 아니라 **탐욕적 최단경로 = 인코스**다.

> 지금 관측되는 인코스 파고들기는 버그가 아니라, 짧은 horizon + 진행 보상 조합의 수학적 필연이다. 자유도를 줬더니 그 자유도로 최단경로를 골랐을 뿐이다.

#### (b) 제약 없는 방향의 최적해는 항상 제약면 위에 앉는다 ← 핵심

최적화 이론의 기본 성질이다. `q_dist = 0`이면 횡방향(e_y)에 대해 비용이 평평하고, 유일한 횡방향 힘은 벽에서 `safe_dist = 0.65 m` 안쪽에서만 켜지는 boundary cost다. 그러면 최적해는 정확히 **"페널티가 막 켜지기 시작하는 지점"에 딱 붙는다.** 그 지점의 robustness margin은 정의상 0이다.

따라서 모델 오차 / 슬립각 오차 / 서보 지연 중 **하나만 있어도 다음 사이클에 전 샘플이 밖으로 나간다.**

> "모든 샘플이 바운더리를 나가면 더 심하다"는 관측은 우연한 사고가 아니라, 이 설계가 매 코너마다 스스로 만들어내는 정상 귀결이다.

MPC 용어로는 **recursive feasibility가 보장되지 않는 상태**다. 사이클 k의 최적 계획이 사이클 k+1에서 feasible한 연속 계획이 존재하지 않는 상태로 끝난다. 표준 해법은 terminal constraint(마지막 상태가 여유를 갖고 트랙 안에 있을 것 + 남은 코리도 안에서 정지 가능할 것)를 거는 것이다.

#### (c) rejection이 "비었을 때"를 정의하지 않는다

feasible 샘플이 **하나라도 있으면** 현재 구현은 의도대로 동작한다. λ=15, fault 비용 10000이면 `exp(-10000/15) ≈ 0`이라 가중치가 정확히 0이 된다. 소프트 페널티지만 실질적으로 hard rejection이다. **이 부분은 문제없다.**

문제는 전부 infeasible일 때다. 비용이 전부 7600~9600 근방으로 뭉치면서 서로 가중치를 나눠 갖고, 그 순위를 결정하는 건 [mppi_core.cu:362-370](../src/mppi_core.cu#L362-L370)이다.

```cpp
total_cost += 10000.0f - (float)t * 50.0f;      // 늦게 박을수록 이득
total_cost -= p.q_v * (float)progress * 5.0f;   // 멀리 가서 박을수록 이득
```

측정값 (1 m 앞 벽 기준):

| 충돌 시 속도 | t_impact | 비용 |
|---|---|---|
| 4.0 m/s | 7 | 9601 |
| 2.0 m/s | 14 | 9251 |
| 0.6 m/s | 47 | 7600 |

느리게 박는 쪽이 유리하긴 하다. 하지만 **충돌 속도 자체가 비용에 들어가지 않는다.** 4 m/s로 박든 0.6 m/s로 박든 기본 10000은 동일하고, 차이는 "몇 스텝을 버텼나"에서만 나온다. 그리고 progress 항이 반대 방향으로 당긴다.

여기에 fill control이 겹친다 — [mppi_core.cu:374-376](../src/mppi_core.cu#L374-L376):

```cpp
float survival_steer = controls[k * T + t].steer * 0.1;  // 조향 1/10로 죽임
Control safe_control = {survival_steer, -2.0f};          // min_accel(-8.0) 미사용
```

전 샘플 fault 시 가중평균의 대부분 구간이 이 값으로 채워지고, 그게 `h_prev_controls_`로 시프트되어 **다음 사이클 warm start까지 오염된다.** 결과가 "핸들 풀고 -2로 살살 감속하면서 벽으로"다.

> **S2가 의도된 동작이라는 건 이해했다.** 다만 "감속만 한다"와 "감속하면서 조향까지 포기한다"는 다르다. 후자는 의도가 아닐 것이다. 그리고 전 샘플 fault 시의 순위가 racing cost의 변형이라는 점은 재검토가 필요하다 — 그 상황에서는 racing을 완전히 버리고 다른 문제(충돌에너지 최소화)를 풀어야 한다.

또한 참고로 [mppi_core.cu:541](../src/mppi_core.cu#L541)의 비상정지 분기는 도달 불가능하다.

```cpp
if (std::isinf(min_cost) || min_cost >= 1.0e8f) { ... {0.0f, -5.0f} ... }
```
fault 비용의 최대치가 ~1e4이므로 1e8은 NaN일 때만 나온다. 의도된 감속 정책이라면 이 dead branch는 제거하거나 임계를 현실값으로 낮춰야 혼란이 없다.

#### 권고 방향 (q_dist는 계속 0으로 두되)

| 조치 | 효과 | 비용 |
|---|---|---|
| horizon T=50 → 85 (3 s) | out-in-out이 실제로 보이기 시작 | GPU 시간 1.7배 |
| 오프라인 전역 레이싱라인을 reference로 | 진짜 레이싱 라인. corridor 자유도는 추월 전용 | 오프라인 툴 필요 |
| boundary cost를 전폭 매끄러운 barrier로: `(2·e_y/w_total)^6` | 중앙 근처 비용 ≈0(라인 자유도 유지) + gradient 존재 → 최적해가 제약면에 안 붙음 | 거의 없음 |
| lexicographic fallback | feasible 있으면 그 안에서만, 없으면 다른 cost | 커널 수정 소 |

`(2e_y/w)^6` barrier의 성질: `e_y/w_half = 0.5`에서 비용 계수 0.016, `0.8`에서 0.26, `0.95`에서 0.74, `1.0`에서 1.0. 즉 트랙 폭의 80%까지는 사실상 공짜라 라인 자유도를 해치지 않으면서, 벽 근처에서만 급격히 서는 gradient를 만든다.

### A-2. 진행/속도 보상이 3중이다 (추가 설명)

**"왜 3개가 문제인가"부터.**

최적제어에서 비용함수는 "무엇이 좋은 것인가"의 정의 그 자체다. 그래서 항이 여러 개일 때 중요한 건 각 항의 절대값이 아니라 **항들 사이의 교환비(trade rate)** — "벽에 10 cm 더 붙는 대가로 속도를 얼마나 얻을 수 있나"다.

현재 진행/속도를 보상하는 항이 세 개다.

| 위치 | 항 | 성격 | 크기 |
|---|---|---|---|
| [:157](../src/mppi_core.cu#L157) | `-(q_v·0.2)·v·cos(Δψ)` | **스텝마다** | 0.8/step × 50 = 40 |
| [:401](../src/mppi_core.cu#L401) | `-q_progress·progress` | **종단 1회** | 36 × 최대 60 = 2160 |
| [:405](../src/mppi_core.cu#L405) | `-q_escape_vel·v²` | **종단 1회** | 32 × 16 = 512 |

문제 세 가지:

**(i) 셋 다 같은 물리량(경로 진행)을 측정하는데 단위와 포화 특성이 다르다.** `q_v`를 만지면 `vel_cost`뿐 아니라 fault 시 progress 보상([:370](../src/mppi_core.cu#L370)의 `p.q_v * progress * 5.0`)까지 같이 움직인다. 어느 항이 실제로 지배적인지 파라미터만 봐서는 알 수 없고, 하나를 튜닝하면 나머지의 실효 가중치가 바뀐다.

**(ii) 스텝별 항과 종단 항을 섞어놨다.** `vel_cost`는 50번 누적되므로 파라미터에 적힌 숫자보다 50배 세다. 반대로 종단 항은 한 번만 들어간다. 표에서 보듯 실제로는 종단 항이 50배 지배적인데, 파라미터 파일만 보면 `q_v: 1.0` vs `q_progress: 36.0`이라 36배 차이로 읽힌다. 실제는 `40 : 2160`, 54배다.

**(iii) 벽 페널티와의 교환비가 1:2다.** 측정값:

```
코너컷 이득 : progress 2칸(20cm) = 72  +  탈출속도 +0.5 m/s = 136   →  합 208
벽 0.35 m로 6스텝 스치는 비용                                    →  400
```

같은 자릿수다. 노이즈 한 번, 모델 오차 한 번이면 뒤집힌다. **벽 페널티는 코너컷 이득보다 최소 한 자릿수 위여야 한다.**

**표준적인 처방**: 진행 보상은 **하나만** 남긴다. 스텝마다 주는 arc-length 증분 `-q_s·(s[t] - s[t-1])`가 표준이다. 속도는 그 자체로 보상하지 않는다 — 빨리 가면 arc-length가 저절로 늘어나므로 중복이다. 나머지는 전부 제약이나 페널티로 표현한다.

### A-3. 그립 한계 페널티가 포화한다 (추가 설명) ← 제어이론적으로 가장 심각

**비유부터.** 최고 100 km/h까지만 표시되는 속도계로 과속 단속을 한다고 하자. 120으로 달리든 200으로 달리든 계기판은 100을 가리키고 벌금이 같다. 그러면 200으로 달리지 않을 이유가 없다.

현재 `lat_g_cost`가 정확히 그 구조다.

```cpp
float ay_abs = fabsf(s.ay);                          // 모델이 "실제로 낸" 횡가속도
float lat_g_over = ay_abs - p.lat_g_threshold;       // 5.5
float lat_g_cost = (lat_g_over > 0) ? q_lat_g * lat_g_over² : 0;
```

`s.ay`는 타이어 힘에서 나온다 — `ay = (F_fy·cos δ + F_ry)/m`. 그런데 파세이카 모델의 힘에는 물리적 상한이 있다.

```
ay_max = (F_zf·D_f + F_zr·D_r)/m = (18.23×0.7955 + 18.46×0.7317)/3.74 = 7.38 m/s²
```

따라서:

1. **`lat_g_fault_threshold: 9.0`은 절대 발동하지 않는다.** 모델이 9를 낼 수 없다. [mppi_core.cu:348](../src/mppi_core.cu#L348)의 하드 페일 체크는 완전한 dead code다.
2. **soft 페널티는 `500 × (7.38 - 5.5)² = 1760`에서 상수로 포화한다.** 그 이상 무리해도 추가 비용이 0이다.

결과: **코너를 3.8 m/s로 돌든 4.0 m/s로 돌든 `ay`는 똑같이 7.38로 포화되어 같은 비용을 낸다.** 그런데 4.0 쪽이 progress/escape 보상을 더 받는다. 즉 **그립 한계를 넘어선 뒤로는 속도가 공짜다.**

여기에 곡률 기반 속도 프로파일도 없다. README에는 "z 성분에 목표 속도 삽입"이라 적혀 있지만 [path_publisher.cpp:162](../src/path_publisher.cpp#L162)는 `position.z = 0.0`을 넣고 `smppi_node`는 z를 읽지 않는다. **비용함수 어디에도 "코너 앞에서 감속하라"는 항이 없다.** 유일한 감속 압력이 위의 포화하는 lat_g뿐이다.

**고쳐야 할 방향 — "달성값"이 아니라 "요구값"에 페널티를 건다.**

| 지표 | 성격 | 포화? |
|---|---|---|
| `s.ay` (현재) | 타이어가 실제로 낸 힘 | **포화 (7.38)** |
| `v²·κ_ref` | 이 속도로 이 곡률을 돌려면 필요한 횡가속도 | 포화 안 함 |
| `α_r - α_r_peak` | 후륜 슬립각이 피크(0.131 rad)를 넘은 양 | 포화 안 함 |

`v²κ`는 속도가 오르면 계속 커진다. `v²κ - ay_max`가 양수면 "이 속도로는 물리적으로 이 코너를 못 돈다"는 뜻이고, 그 초과분에 페널티를 걸면 제대로 된 감속 압력이 된다. `κ`는 센터라인에서 오프라인으로 미리 계산해 `ref_yaws`처럼 GPU에 올려두면 된다.

부수적으로 `lat_g_fault_threshold`도 7.38 미만(예: 7.0)으로 내려야 살아난다.

### A-4. progress 보상이 3.39 m/s에서 포화한다 (추가 설명)

[mppi_core.cu:395-401](../src/mppi_core.cu#L395-L401):

```cpp
int progress = local_path_idx - initial_path_idx;   // 웨이포인트 "칸 수"
if (progress < -path_len / 2) progress += path_len; // 루프 랩어라운드 보정
int max_possible_progress = T + 10;                 // = 60
progress = max(0, min(progress, max_possible_progress));
total_cost -= p.q_progress * (float)progress;
```

**무슨 일이 벌어지나:**

```
60칸 × 0.099 m/칸 = 5.9 m
horizon 1.75 s 동안 5.9 m를 가는 속도 = 3.39 m/s
max_speed = 4.0 m/s
```

**3.39 m/s를 넘는 순간 모든 샘플의 `progress`가 똑같이 60으로 클램프된다.** 그러면 `q_progress` 항이 모든 샘플에 동일한 상수가 되어 **샘플을 구분하는 능력을 완전히 잃는다.** 최적화 용어로 gradient가 0이 된다.

그 구간에서 속도를 구분하는 항은 `q_escape_vel · v²` 하나만 남는다. 이건 "종단 속도 최대화"라 위치를 전혀 고려하지 않는다 → **가장 조인 라인**이 이긴다. 트랙에서 빠른 구간이 곧 코너 진입 구간이므로, 하필 제일 위험한 곳에서 이 현상이 발생한다.

**왜 클램프가 붙어 있나**: 랩어라운드 처리가 완전하지 않을 때 `progress`가 터무니없는 값이 될 수 있어서 방어용으로 넣은 것으로 보인다. 특히 icra2025 맵은 1110점인데 [mppi_core.cu:481](../src/mppi_core.cu#L481)에서 1000점으로 잘려 루프가 안 닫힌다 (11 m 점프). map1(256점)은 무사하다.

**추가 위험**: progress를 **칸 수**로 세므로 웨이포인트 간격에 암묵적으로 의존한다. map1은 0.099 m 균일이라 지금은 괜찮지만, 누가 센터라인 CSV를 다른 해상도로 다시 뽑으면 `q_progress`의 물리적 의미가 조용히 바뀐다. **arc-length(m)로 세야 한다.** CSV에서 누적 s를 미리 계산해 GPU에 올리면 된다.

## B. 모델 / 상태추정

### B-1. 충돌 판정이 base_link 한 점 + 원 하나

[mppi_core.cu:263](../src/mppi_core.cu#L263)이 반환하는 건 `(x, y)` **한 점**에서 벽까지의 거리이고, `collision_radius = 0.3`인 원 하나로 차를 대신한다.

실제로는 앞범퍼가 base_link(후축)보다 약 0.35~0.40 m 앞에 있다. 코너에서 차체가 벽에 대해 15~20° 틀어져 있으면 **앞안쪽 모서리가 원 모델보다 `L·sin(Δψ) ≈ 0.10~0.14 m` 더 안쪽으로 나간다.** 플래너가 "0.35 m 여유"라고 본 게 실제로는 0.21 m다.

**직사각형이 정답이지만, 원 3개 근사를 권한다.** GPU 커널에서 rect-vs-polyline 거리는 분기가 많아 비싸고, F1TENTH 차체(약 0.50 × 0.28 m)는 반경 0.15 m 원 3개를 축방향 0.155 m 간격으로 놓으면 오차 3 cm 이내로 덮인다. 기존 `compute_min_boundary_distance`를 3번 호출해 min만 취하면 끝난다.

```
disk 중심 (base_link 기준 차체 x축): -0.02, +0.135, +0.29   반경 각 0.15
```
(정확한 값은 실제 차량 실측 후 확정)

### B-2. 슬립각이 항상 0으로 들어간다 — EKF만으로는 안 고쳐진다

[smppi_node.cpp:106-107](../src/smppi_node.cpp#L106-L107):
```cpp
current_state_.slip_angle = std::atan2(current_state_.vy, std::fabs(current_state_.v) + 1e-5f);
```
`vy`가 0이면 `slip_angle`도 0이다. 그리고 **연쇄가 세 군데 끊겨 있다.**

| # | 위치 | 문제 |
|---|---|---|
| 1 | `vesc/vesc_ackermann/src/vesc_to_odom.cpp:157` | `twist.linear.y = 0.0` 하드코딩. 횡속도 센서가 없으니 당연 |
| 2 | `ekf_pose/src/ekf_pose_estimator.cpp:296` | `H(1,4) = 1.0` — **EKF가 그 가짜 0을 vy 측정치로 융합한다** |
| 3 | `vesc/vesc_ackermann/src/vesc_to_odom.cpp:111` | `angular.z = v·tan(δ)/L` — omega도 측정이 아니라 무슬립 운동학 재구성값 |

특히 2번이 핵심이다. EKF는 예측 단계에서 `vy += (ay + vx·yr)·dt`로 IMU 기반 vy를 제대로 뽑아놓고([ekf_pose_estimator.cpp:181](../../../ekf_pose/src/ekf_pose_estimator.cpp#L181)), update 단계에서 그걸 0으로 다시 끌어내린다. 그래서 **`/ekf_odom`의 vy도 ≈0이다. 지금 상태로 토픽만 `/ekf_odom`으로 바꾸면 아무것도 달라지지 않는다.**

이 사실은 이미 [pacejka_sysid/state_assembler.py:7-11](../../pacejka_sysid/pacejka_sysid/state_assembler.py#L7-L11)에 정확히 문서화되어 있다.

**영향**: 코너에서 실제 β는 0.10~0.15 rad인데 플래너는 매 사이클 "차가 똑바로 가고 있다"고 가정하고 horizon을 시작한다. 전륜에 남은 그립을 체계적으로 과대평가하게 되고, 실제보다 더 조이는 라인을 그린다. **코너에서만 나타나고, 방향도 안쪽이다.** A-1(b)에서 말한 "제약면에 딱 붙은 최적해"의 마진을 정확히 이 오차가 갉아먹는다.

**해결 옵션 3가지:**

| 옵션 | 내용 | 난이도 |
|---|---|---|
| ① state_assembler 재사용 | `pacejka_sysid`의 `v̇y = a_y - v_x·ω` + 워시아웃 로직을 포팅 | 중 |
| ② EKF 수정 | `H`에서 vy 행 제거(3×6 → 2×6). vy는 IMU 예측만으로 | 소 |
| ③ 준정상 근사 | `β ≈ atan(l_r·ω/v)` 한 줄 | 최소 |

> ### ⚠ 정정 (2026-08-03, 실차 bag 검증 후) — ①은 기각, **③이 정답**
>
> 처음에는 ①(state_assembler 의 IMU 적분)을 1순위로 권고했으나, 0730 실차 bag +

## C. 샘플러 / 적분기 (비제어 배경용 설명)

A·B와 독립적으로 존재하는 문제들이다. **A·B를 다 고쳐도 이게 남으면 코너에서 반응 자체를 못 한다.**

### C-1. 샘플러가 회피 기동을 아예 만들지 못한다 ← 가장 큰 것

**MPPI가 어떻게 동작하는지부터.** 8000개의 제어 시퀀스 후보를 랜덤하게 만들고, 각각을 시뮬레이션해서 비용을 매기고, 좋은 것에 큰 가중치를 줘서 평균 낸다. 즉 **후보 집합 안에 없는 동작은 절대 나올 수 없다.** "핸들을 확 꺾어 피하는" 샘플이 8000개 중에 하나도 없으면, MPPI는 그 동작을 발견할 방법이 없다.

지금 후보를 어떻게 만드는가 — [mppi_core.cu:307-332](../src/mppi_core.cu#L307-L332):
1. 백색 노이즈를 뽑고 (`std = 0.4 rad/s`)
2. 2차 버터워스 저역통과 필터로 부드럽게 만들고 (SMPPI의 핵심 — 조향이 덜덜 떨리지 않게)
3. `× dt`를 곱해 **조향 증분**으로 쓴다 (조향 자체가 아니라 변화량)

문제 두 가지가 곱해진다.

**(i) 필터 상태를 매 롤아웃마다 0으로 초기화한다** ([:292-295](../src/mppi_core.cu#L292-L295)). 버터워스 계수가 `b0 = 0.073`이라, 필터가 처음 켜지는 t=0~2 구간의 출력이 정상값의 1/10 이하다.

**(ii) 노이즈가 조향 증분에 들어가므로 랜덤워크로 누적된다.** 초반에 작으면 끝까지 작다.

실측 결과 (8000 샘플 시뮬):

| t | 조향 탐색 폭 (표준편차) | 비고 |
|---|---|---|
| 0 | **0.0010 rad (0.06°)** | ← **실제로 차에 나가는 스텝** |
| 5 | 0.025 rad (1.4°) | |
| 25 | 0.067 rad (3.8°) | |
| 49 | 0.096 rad (5.5°) | |

`max_steer = 0.4788 rad (27°)`이다. **horizon 끝에서도 ±5.5°밖에 탐색하지 못한다.** 8000개를 뽑아도 전부 "이전 계획 ± 아주 조금"의 미세 변형이고, 실질적으로 서로 거의 같은 궤적이다.

**결과**: 벽 앞에서 감속만 하는 이유의 절반이 이거다. **핸들을 꺾는 샘플이 존재하지 않으니 꺾을 수가 없다.** warm start를 매 사이클 시프트하므로 여러 사이클에 걸쳐 조금씩 옮겨갈 수는 있지만, 유효 폐루프 대역폭이 대략 1.5~3 Hz다. 4 m/s에서 코너 수정을 하기엔 한참 느리다.

**고치는 법** (둘 중 하나):
- 필터 상태를 정상상태 분산으로 초기화 (한 번 미리 warm-up 돌려서 그 분포에서 뽑기)
- 처음 5스텝만 필터를 우회하고 raw 노이즈를 쓴다 (SMPPI의 부드러움은 주로 중후반 구간에서 필요하다)

### C-2. λ(온도)가 비용 스케일과 안 맞는다

MPPI의 가중치는 `w_k ∝ exp(-(J_k - J_min)/λ)`다. λ는 "비용이 얼마나 차이 나야 의미 있게 다른 것으로 볼 것인가"를 정하는 스케일이다.

- λ가 비용 스프레드보다 **너무 작으면**: 최소비용 샘플 하나만 가중치 1을 갖고 나머지는 0 → MPPI가 그냥 "8000개 중 제일 좋은 거 하나 고르기(argmin)"로 퇴화한다. 평균의 분산 감소 효과가 사라져 명령이 사이클마다 튄다.
- λ가 **너무 크면**: 전부 균등 가중 → 그냥 이전 계획 유지.

현재 λ=15인데 비용 스프레드는 10³~10⁴다. **완전히 전자에 해당한다.**

진단 방법: **유효 표본 수** `ESS = (Σw)² / Σw²`를 로깅한다. 8000개를 뽑았는데 ESS가 1~2로 나오면 7998개가 낭비되고 있다는 뜻이다. 건강한 값은 K의 5~20% 정도다. λ를 스윕하면서 ESS를 보는 게 가장 빠른 튜닝 방법이다.

역설적으로, 전 샘플이 fault나면 비용이 서로 몇백 이내로 뭉쳐서 그때만 갑자기 가중치가 넓게 퍼진다. 그리고 그 평균의 내용물이 A-1(c)의 `{0.1·steer, -2.0}`이다.

### C-3. 오일러 적분이 저속 요(yaw) 과도응답에서 진동한다

**적분기 안정성 개념.** 미분방정식을 컴퓨터로 풀 때 `x[k+1] = x[k] + dt·ẋ` (전진 오일러)를 쓰면, 시스템이 빠를수록 `dt`가 작아야 한다. 기준은 `dt < 2/|λ|` (λ = 시스템 극점). 이걸 넘으면 계산 결과가 **발산하거나 진동한다 — 물리와 무관하게 순수한 수치 아티팩트다.**

이 차량의 요 동역학 극점은 속도에 반비례한다 (느릴수록 빠른 시스템이 된다):

| v [m/s] | 연속 극점 [1/s] | 오일러 \|z\|max | 판정 |
|---|---|---|---|
| 1.0 | -74 / -180 | 5.29 | **불안정** |
| 1.5 | -52 / -117 | 3.11 | **불안정** |
| 2.0 | -42 / -85 | 1.98 | **경계** |
| 2.5 | -37 / -65 | 1.27 | 경계 |
| 3.0 | -36 / -49 | 0.72 | 진동 |
| 4.0 | -32 ± 10j | 0.38 | OK |

`dt = 0.035 s`의 안정 한계는 `|λ| < 57 1/s`다. **2.5 m/s 아래가 전부 한계 밖이다.**

실제 스텝 조향 응답 (ω, rad/s) — 같은 물리, 같은 입력, 적분만 다르게:

```
v=1.5  Euler(35ms):  1.51  1.25  2.86  0.86  2.05  0.98  3.19 ...  ← 수렴 안 함
       참값(1/16dt): 1.01  1.50  1.65  1.68  1.69  1.69  1.69 ...

v=2.0  Euler(35ms):  1.51  1.65  2.30  1.87  2.28  1.90  2.26 ...  ← ±10% 지속 링잉
       참값(1/16dt): 1.06  1.62  1.90  2.01  2.06  2.07  2.08 ...

v=4.0  Euler(35ms):  1.51  2.29  2.39  2.29  2.15 ...              ← 첫 스텝 30% 과대
       참값(1/16dt): 1.16  1.71  1.92  1.97  1.95 ...
```

**해석**:
- **v ≤ 2 m/s (코너 최저속 구간)에서는 궤적 자체가 무의미하다.** 진동은 물리가 아니라 적분 오차다.
- **v = 4 m/s에서도 첫 스텝 요레이트를 30%, 3스텝 피크를 21% 과대평가한다.** 정상상태는 비선형 포화 덕에 맞지만, 턴인 과도구간이 틀린다. 즉 **플래너는 자기 자신의 물리 모델보다도 차가 더 잘 돌아간다고 믿고 라인을 그린다.**

**고치는 법**: 요/슬립 동역학 부분만 서브스텝 2~4분할 또는 RK2. 위치 적분(x, y)은 지금 그대로 둬도 된다. GPU 커널 비용은 요 동역학 부분만 늘어나므로 전체 20~30% 증가 예상.

### C-4. 후륜 타이어 형상이 비물리적이다

`C_r = 2.2129`는 승용 타이어의 통상 범위(1.3~1.8)를 크게 벗어난다. 파세이카에서 `C`는 피크 이후 힘이 얼마나 떨어지는지를 결정하는 형상 계수다.

| α_r [rad] | F_yr [N] |
|---|---|
| 0.131 (피크) | 13.51 |
| 0.20 | 12.11 |
| 0.30 | 8.89 |
| 0.50 | 4.45 |
| 1.20 | **-0.60 (부호 반전)** |

피크 이후 67% 붕괴하고 결국 부호가 뒤집힌다. 실제 타이어는 피크 후 10~20%만 감소한다.

**영향**: 모델상 후륜이 한 번 미끄러지면 회복 불가능한 스핀이 된다. MPPI가 그 영역을 극단적으로 회피하므로 **리커버리 기동을 학습할 수 없다.** sysid 피팅 시 `C`에 상한(≤1.8)을 제약으로 걸고 다시 뽑는 게 맞다.

### C-5. 종/횡 그립 커플링(마찰원)이 없다

```cpp
float dot_vel = u.accel * (1.0f - p.Cm0 * vel);   // 타이어를 안 거친다
```
종방향은 명령한 가속도가 그대로 나오고, 횡방향만 파세이카로 포화한다. **모델은 -8 m/s² 제동과 7.4 m/s² 횡가속을 동시에(합 11 m/s² ≈ 1.1 g) 낼 수 있다고 믿는다.** 실제 μ가 0.7~0.8이면 불가능하다. 마찰원 제약 `√(a_x² + a_y²) ≤ μg`가 없으니 트레일브레이킹으로 아펙스까지 깊게 파고드는 계획이 나온다.

### C-6. 기타

- **지연 보상 없음**: 측정 상태에서 바로 풀지만 명령은 1주기 + 서보 지연(≈50~70 ms) 뒤에 먹는다. 4 m/s에서 20~28 cm. `solve()` 전에 상태를 지연만큼 전진시켜야 한다.
- **상태 동기화 없음**: `use_mcl_pose` 모드에서 pose(`/newmcl_pose`)와 twist(`/odom`)를 서로 다른 시각에 받아 타임스탬프 체크 없이 합친다.
- **`q_du` 단위 혼재**: `q_du·(d_steer² + d_accel²)`에서 `d_accel²`(O(1~9))가 `d_steer²`(O(4e-5))를 완전히 압도한다. 조향 레이트 페널티는 사실상 없다. 가중치 분리 필요.
- **`vel_cost`의 방향**: `cos(yaw - ref_yaw)`를 쓰는데 진행 방향은 `yaw + slip_angle`이다. "가리키는 방향"이 아니라 "가는 방향"으로 보상해야 한다.
- **`dot_slip` 누락항**: `cos(δ-β)`, `cos β` 생략. δ=0.4에서 전륜 힘 8% 과대. 위 항목들에 비하면 무시할 수준.
- **경로 1000점 절단**: [mppi_core.cu:481](../src/mppi_core.cu#L481). icra2025(1110점)에서 110점(≈11 m)이 잘려 루프 폐합이 깨진다. map1(256점)은 무사.

## D''. 시뮬 closed-loop 검증 (2026-08-03)

### 환경 문제 — CUDA 커널이 조용히 실패할 수 있다 (별도 이슈, 우선 조치 권고)

`racecar_simulator` + `smppi_cuda_controller`를 헤드리스로 붙여 map1에서 closed-loop
검증을 시도했는데, **첫 시도에서 차가 스폰 직후 조향각 0.0(비트 단위로 정확히 0)을
영원히 내며 트랙 밖으로 직진**했다. 원인은 진단 내용과 무관했다 — 검증에 쓴 GPU
(RTX 2080 SUPER, Turing/compute_75)가 [CMakeLists.txt:21](../CMakeLists.txt#L21)의
`CMAKE_CUDA_ARCHITECTURES "86;89"`(Ampere/Ada)에 없어서 **모든 커널 launch가
`cudaErrorNoKernelImageForDevice`로 실패**했다.

문제는 이게 **완전히 조용하다**는 것이다 — [cuda_mppi_core.hpp:16-22](../include/cuda_mppi_controller/cuda_mppi_core.hpp#L16-L22)의
`CUDA_CHECK`는 `fprintf(stderr, ...)`만 하고 **abort하지 않는다.** 그 결과:

- `h_costs_`가 device에서 한 번도 안 채워져 생성자의 zero-init 값(전부 0.0)으로 남는다
- 전 샘플 비용이 0으로 동일 → 가중평균이 zero-init된 `h_controls_`(전부 `{0,0}`)의 평균 → **정확히 0**
- `/drive`가 `steering_angle=0.0, speed≈min_speed`를 정상 로그와 함께 계속 발행한다 — **에러 로그를 stderr에서 직접 안 보면 "잘 도는데 그냥 직진하네" 정도로만 보인다.**

**이건 실차에서도 재현 가능한 안전 문제다.** Jetson 드라이버/CUDA 버전이 조금만
어긋나도(런타임 업데이트, 이미지 재설치 등) 동일 실패 모드가 나온다. 지금 코드는
그 상황에서 **에러도 안 내고 그냥 "직진"한다.**

**권고 (별도 작업, 이번 진단 범위 밖)**:
- `CUDA_CHECK`가 커널 launch/`cudaDeviceSynchronize` 실패 시 **최소한 `is_healthy_` 플래그를 내리고, `smppi_node`가 그 플래그를 보고 `/drive`에 0속도·풀브레이킹을 강제 발행**하도록. 지금처럼 "정상 출력처럼 보이는 침묵"이 제일 위험하다.
- 또는 `MPPISolver` 생성자에서 `cudaGetLastError()`로 최초 커널 launch 성공을 확인하고 실패 시 예외를 던져 노드 자체가 뜨지 않게.

이번 검증에서는 **로컬 스크래치에서만 임시로 `CMAKE_CUDA_ARCHITECTURES`에 `75`를
추가해 재빌드** → 검증 완료 후 원복했다 (`CMakeLists.txt`는 커밋된 상태 그대로).

### closed-loop 결과 (아키텍처 수정 후, 90초, map1, 8000샘플)

동일**하다(둘 다 `B_f 6.0926 C_f 1.2447 D_f 0.7955 ... `). 즉 플래너 내부 모델이

## D''''. Phase 3 구현 + 시뮬 A/B (2026-08-04)

A절 진단(비용함수 설계)의 두 처방을 구현하고, **조건당 6회 60초** 시행으로 A/B 했다.

### 구현

| 태그 | 내용 | 코드 |
|---|---|---|
| **3-C** | 트랙 전폭 barrier `q_barrier · (e_y/half_width)^6` | `compute_cost_cuda` |
| **3-B** | 그립 페널티를 곡률 속도한계 `v_lim=√(lat_g_threshold/\|κ\|)` 초과분으로 | `compute_cost_cuda` |

### 판정

**1. barrier 는 명확한 승리 — 속도와 안전이 동시에 좋아진다.**
거리 +24%, 이탈 36.2%→14.2%(유의). 보통 이 둘은 트레이드오프인데 함께 개선됐다.
**A-1(b) 진단("최적해가 제약면에 딱 붙어 robustness margin 이 0")이 옳았다는 직접
증거다** — 최적해를 제약면에서 떼어놓으니 이탈이 줄고, 이탈이 줄어 되돌아오는 데
쓰던 시간이 사라져 오히려 더 멀리 갔다. 시행간 표준편차도 27.2→16.8 로 줄었다.

**2. barrier 는 셀수록 좋은 게 아니다.** 5000 은 2000 보다 나쁘다
(이탈 14.2→24.3%, std 3.9→17.9). 너무 세면 센터라인으로 밀어붙여 빠른 라인을
못 쓰고 다시 불안정해진다. **2000 근방이 최적.**

**3. 곡률 그립은 이탈을 완전히 없앤다.** 6회 전부 0.0%, 거리 표준편차 1.2~2.7 m
(base 27.2 m) — **재현성이 10배 개선**. "가끔 코스를 벗어나 헤맨다"는 이봉분포가
사라졌다. 대신 속도를 낸다.

**4. 최적 조합 = barrier 2000 + 곡률그립 th 7.0.**
거리 113.8 (base 117.4 와 통계적 차이 없음)인데 **이탈 0%, std 2.7 m**.
즉 **속도를 잃지 않으면서 코스아웃을 완전히 제거하고 거동을 예측 가능하게** 만든다.
th 5.5 는 너무 보수적이라 거리가 95 m 로 떨어진다 (모델 상한 7.38 대비 여유 과다).

- **perfect-model 시뮬 결과다.** 시뮬 타이어 파라미터가 SMPPI 내부 모델과 동일하다
  (D'' 절). 실차엔 모델 불일치가 있으므로 절대 수치는 재현되지 않는다. 다만 barrier 의

### Phase 3 — 비용함수 구조 (A절)

**3-A. 진행 보상 통합** (A-2, A-4)

- [ ] 센터라인 CSV 로드 시 누적 arc-length `s[i]` 계산 → GPU에 업로드
- [ ] `progress`를 칸 수 → **미터**로 변경. `q_progress` 재튜닝 (칸→m 환산: 현재 36/칸 ÷ 0.099 m/칸 = 364/m 상당)
- [ ] `max_possible_progress` 클램프를 `v_max·T·dt·1.2`로 (또는 랩어라운드를 제대로 처리하고 클램프 제거)

- [ ] `vel_cost` 제거 검토 — 마찬가지로 중복. 남긴다면 `cos(yaw + slip_angle - ref_yaw)`로 수정
- [ ] `q_du`를 `q_du_steer` / `q_du_accel`로 분리

**3-B. 그립 페널티를 요구값 기준으로** (A-3)

- [ ] 센터라인 CSV 로드 시 곡률 `κ[i]` 계산 → GPU 업로드
- [ ] `lat_g_cost`를 `s.ay` 대신 `v² · κ[nearest_idx]` 초과분 기준으로 변경
  ```cpp
  float ay_req = s.v * s.v * fabsf(kappa[nearest_idx]);
  float over = ay_req - p.lat_g_threshold;
  float lat_g_cost = (over > 0) ? p.q_lat_g * over * over : 0.f;
  ```
- [ ] `lat_g_fault_threshold` 9.0 → 7.0 (모델 상한 7.38 미만이어야 발동)
- [ ] **검증**: 코너 진입 전 감속이 실제로 걸리는지. `/mppi_optimal_trajectory`의 accel 시퀀스로 확인

**3-C. 경계 비용을 전폭 barrier로** (A-1 권고)

- [ ] `compute_min_boundary_distance`가 `min_dist`와 함께 정규화 횡편차 `e_norm = 2·e_y/w_total`도 반환
- [ ] 상시 barrier 추가: `q_barrier · pow(e_norm, 6)`
  - `|e_norm| < 0.8`에서 거의 0 → **라인 자유도 유지**
  - `|e_norm| → 1`에서 급증 → 최적해가 제약면에 딱 붙지 않음
- [ ] 기존 `soft_cost`/`hard_cost`는 유지 (충돌 직전 방어선)
- [ ] `q_barrier` 초기값: 코너컷 이득(≈208)의 10배가 벽 근처에서 나오도록 → 2000 근방부터 스윕

**3-D. fallback 정책 분리** (A-1(c))

> S2의 "감속만 한다"는 의도된 동작이므로 그 자체는 유지. 순위 로직만 고친다.

- [ ] fault 비용에 충돌속도 항 추가: `+ q_impact · v²` (`q_impact` ≈ 300)
- [ ] fault 시 `progress` 보상 제거 (`-= q_v·progress·5.0` 삭제) — 이게 "멀리 가서 박기"를 유도한다
- [ ] fill control의 조향 감쇠 `×0.1` 제거 → `u.steer` 그대로 유지. 감속은 의도대로 `-2.0` 유지하되 파라미터로 노출
- [ ] 도달 불가능한 `min_cost >= 1.0e8f` 분기 제거 또는 임계를 현실값으로
- [ ] (선택) 전 샘플 fault 감지 시 별도 fallback: `min_cost > 5000`이면 racing cost를 버리고 clearance 최대화 샘플 선택
